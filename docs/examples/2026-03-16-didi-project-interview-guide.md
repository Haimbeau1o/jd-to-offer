# 滴滴项目面试讲解手册

## 这份文档解决什么问题

这不是一份“项目说明书”，而是一份“面试讲法手册”。

目标是帮你在打开网页 demo 时，不只是介绍功能，而是把下面三件事一起讲出来：

- 这个项目为什么值得做
- 你在里面到底负责了什么
- 你具备哪些工程、Agent、评测、业务理解能力

---

## 一句话先定项目

这个项目最适合被定义成：

> 我做的不是一个单点问答 demo，而是一个面向滴滴司机经营场景的垂域 Agent 样板间，并且我把它往前延伸到 JD 能力拆解，往后延伸到评测、失败归因和训练数据沉淀，做成了一套从“岗位要求理解”到“项目落地验证”的完整闭环。

这句话非常重要，因为它决定面试官接下来怎么理解你。

如果你只说“我做了一个司机助手”，面试官会把它当成普通 Agent demo。

如果你说“我做了一个从 JD 到能力图谱、再到项目样板和评测闭环的系统”，你的定位会立刻从“会调接口的人”提升到“会做方法抽象和系统设计的人”。

---

## 先把项目结构讲对

这个仓库其实是两层：

### 第一层：JD to Offer 准备引擎

对应代码入口是 `src/jd_offer/cli.py`。

它做的事情是：

1. 读取目标 JD
2. 解析岗位职责、任职要求、加分项
3. 映射成能力 taxonomy
4. 生成知识体系、资源包、项目蓝图、面试素材
5. 输出成固定 case 包

你可以把这一层讲成：

> 我不是先拍脑袋做项目，而是先把 JD 结构化，识别岗位真正要考什么，再反推我应该准备什么知识、做什么项目、最后怎么讲给面试官听。

这层体现的是：

- 需求抽象能力
- 信息结构化能力
- 方法论能力
- 对岗位要求的逆向建模能力

### 第二层：DriverOps Agent Lab

对应核心代码在：

- `src/driverops_agent_lab/agent.py`
- `src/driverops_agent_lab/app.py`
- `src/driverops_agent_lab/eval.py`
- `src/driverops_agent_lab/training_data.py`

这一层才是你打开网页实际展示的部分。

它做的事情是：

1. 接收司机问题
2. 做意图识别
3. 生成多步 plan
4. 调用工具获取司机画像、活动、热区、规则等结构化信息
5. 结合短期和长期 memory
6. 生成 grounded answer、recommendation、risk notes
7. 把 plan、observation、tool trace、memory snapshot 全部返回
8. 继续往后接离线评测、失败归因、训练数据导出

这层体现的是：

- Agent 系统设计
- 工程实现能力
- 数据闭环意识
- 可评测性设计

## 面试时的总讲法

建议你按下面这个顺序讲，不要一上来就讲技术细节。

### 第一段：先讲业务问题

你可以直接这样说：

> 我选滴滴司机经营场景，是因为这个问题天然不是纯 FAQ。司机会问收入为什么下降、今天什么活动适合我、接下来该去哪跑、规则会不会影响资格，这些问题背后都需要把画像、经营统计、活动信息、规则知识和上下文结合起来，所以我用 Agent 的方式来做，而不是只做一个检索问答。

这一段的作用是告诉面试官：

- 你有业务场景判断
- 你知道为什么这里需要 Agent，而不是乱套框架

### 第二段：再讲系统设计

你可以说：

> 这个系统核心链路是 intent router -> planner -> tool execution -> memory -> grounded answer -> evaluator。前端页面只是一个演示入口，真正的核心在后端 Agent 链路和后面的评测闭环。

这时候就可以开始打开网页。

### 第三段：结合网页讲一次完整流程

重点不是“点了按钮出现了结果”，而是顺着返回结果讲系统做了什么。

### 第四段：最后落到评测、训练和迭代

你要把自己从“功能实现者”提升为“系统优化者”。

可以说：

> 我不希望这个项目停留在能跑，所以我又补了 evaluator、failure review 和 training sample export，让它能够往 SFT、偏好优化、奖励设计这条线继续扩展。

## 打开网页后应该怎么讲

`/demo` 页面本身很轻，它只做三件事：

- 输入 `driver_id`
- 输入 `city`
- 输入司机 query
- 调 `/chat`
- 把结果 JSON 原样展示出来

这件事看起来朴素，但面试里其实反而有优势。

因为它不会分散注意力，你可以直接拿返回结构讲系统内部设计。

### 最推荐的讲解顺序

不要一打开网页就上下滚 JSON。

建议固定按这个顺序讲：

1. `intent`
2. `plan`
3. `observations`
4. `recommendations`
5. `memory_snapshot`
6. `stop_reason`

### 为什么按这个顺序

因为这正好对应你的系统流程：

- `intent` 说明系统先做了问题理解
- `plan` 说明系统不是单步回答，而是先规划
- `observations` 说明系统回答有证据来源
- `recommendations` 说明系统最终有行动建议，不只是解释
- `memory_snapshot` 说明系统能利用历史上下文
- `stop_reason` 说明系统不仅能成功结束，还能标记 partial evidence 或 fallback

这样讲出来，面试官会觉得你是按架构在讲，而不是按界面在念。

## 最适合现场 demo 的两个问题

### Demo 1：`今天有什么活动适合我`

这是最稳的一条。

你可以这样讲：

> 我先用活动推荐场景演示，因为它比较完整地覆盖了画像读取、活动匹配和策略建议三个步骤。

然后看页面里的几个字段：

- `intent = campaign_lookup`
- `plan` 里先取画像，再查活动，再生成建议
- `observations` 里能看到命中了两个活动
- `recommendations` 已经把活动和奖励信息转成可执行建议
- `memory_snapshot` 记录了偏好时段和活动偏好

这一段你要强调的不是“查到了活动”，而是：

> 系统先做结构化分解，再做 grounded recommendation，而不是直接生成一句自然语言。

### Demo 2：`帮我看看热区建议`

这条适合接在活动推荐后面讲。

因为这时 memory 已经积累了一轮上下文。

你可以这样讲：

> 第二轮我会故意问热区建议，因为这个场景能体现 memory 的作用。第一次问活动后，系统已经记住了部分偏好和历史推荐，第二轮在 build plan 时会把这些长期记忆带进 reasoning reason 里。

这里你重点看：

- `plan.reason` 里出现长期记忆提示
- `memory_snapshot` 里出现 `preferred_peak_windows` 和 `recent_recommended_zones`
- `recommendations` 里会体现“最近推荐热区仍集中在某区域”

这时候你就把“多轮上下文”“轻量长期记忆”讲出来了。

## 不建议现场主打的 demo

### `完单率规则会影响活动资格吗`

这条现在不建议作为主打 live demo。

原因不是它没价值，而是它目前正好暴露了一个很好的“可优化点”：

- 评测里这条样例期望是 `policy_qa`
- 但当前基线把它分到了 `campaign_lookup`

这其实是你面试里的加分项，不是减分项。

你可以把它当成“我如何发现问题”的例子讲，而不是作为稳定展示路径。

比较好的说法是：

> 我专门保留了 failure review 这部分，因为我不想只展示系统跑通的样子。比如规则问答这个 case，离线评测已经暴露出 intent 分类边界问题。这个问题很典型，因为 query 里同时带了“规则”和“活动资格”，当前规则顺序先命中了活动关键词，所以分类偏掉了。这也是我下一步会优化的地方。

这会让面试官感觉你有工程 honesty，而且能自我校验。

## 你在项目里负责什么，应该怎么讲

这一段必须具体，不能说“我负责了整体开发”就结束。

建议拆成五块讲。

### 1. 需求定义

> 我先不是从模型出发，而是从滴滴司机经营问题出发，收敛出了四个最值得做的高频场景：收入解释、活动推荐、热区建议、规则答疑。

这体现你会做问题收敛。

### 2. 系统设计

> 我设计了从 intent router 到 planner，再到 tool execution、memory、grounded answer 的主链路，并且把 plan、observation、tool trace 这些中间态都保留下来，保证系统可解释、可评测。

这体现你会搭系统，不只是拼接口。

### 3. 工程实现

> 我用 FastAPI 把 demo 服务化，用 Pydantic 约束输入输出 schema，用 Typer 做命令行入口，把在线 demo、离线评测和训练数据导出都做成统一工程结构。

这体现你有工程规范意识。

### 4. 评测闭环

> 我补了 evaluator，不只是看答得像不像，而是看 intent accuracy、tool coverage、plan validity、evidence coverage、fallback rate 这些更贴近 Agent 质量的指标。

这体现你会衡量系统质量。

### 5. 数据沉淀和训练意识

> 我又往后补了 training sample export 和 failure review，让这个 demo 不只是能演示，还能继续接 SFT、偏好优化或者奖励设计实验。

这体现你理解 post-training 和数据 flywheel。

## 面试官最容易感知到的技能亮点

### 亮点 1：你不是做了一个页面，而是做了一个系统

网页只是入口，真正的亮点在：

- intent 分类
- plan 生成
- tool 调度
- evidence 组织
- risk note 生成
- memory 注入
- fallback 处理

### 亮点 2：你有业务映射能力

你做的不是抽象 QA，而是滴滴司机经营问题。

你可以把它映射成这些业务价值：

- 收入解释提升司机对经营波动的理解
- 活动推荐提升激励触达效率
- 热区建议改善供需匹配和在线效率
- 规则答疑减少人工咨询成本

### 亮点 3：你有评测意识

很多人做 demo 到“能回答”就停了。

你这里可以讲：

> 我做完功能后，又加了离线评测，不是只看回答像不像，而是把 Agent 的执行过程拆开看。

### 亮点 4：你有训练闭环意识

你可以讲：

> 我做 training samples 时，不是只保留 user 和 assistant 对话，还把 plan、observations、grounded answer、failure tags 一起导出。这样后面无论做 SFT 还是 preference optimization，都有结构化监督信号。

### 亮点 5：你会诚实面对问题，不回避缺陷

这是很重要的加分项。

比如你可以主动讲：

> 当前 policy QA 仍存在分类边界问题，但我已经通过 evaluation 和 failure review 把它显式暴露出来。对我来说，能看见问题并把问题沉淀成优化入口，比只做一个看起来“都对”的假 demo 更重要。

## 当前前端展示形式的优点和缺点

### 优点

1. 足够轻，注意力不会被 UI 设计分散
2. 直接展示 JSON，适合讲 plan、tool trace、memory 这些内部状态
3. 非常适合技术面，因为每个字段都能映射到系统模块

### 缺点

1. 太“开发者视角”，非技术面试官不容易立刻抓住价值
2. 返回信息很多，如果没有讲解顺序，容易把自己讲乱
3. 没有把“业务价值”和“技术模块”做显式映射
4. 没有把多轮对话中的 memory 变化做对比展示
5. 没有单独的评测面板，无法一眼看出系统闭环

### 结论

当前页面不是“展示型产品界面”，更像“技术 demo 控制台”。

所以最合适的使用方式不是把它当成产品页面讲，而是把它当成一个：

> 让面试官看到 Agent 内部状态流转的可视化调试入口

这个定位一旦讲清楚，页面反而成立。

## 如果你要结合网页来讲，最好的话术模板

下面这段是可以直接练的。

> 这个页面本身很简单，因为我希望面试官看到的重点不是 UI，而是 Agent 的决策过程。  
> 页面会把司机问题直接发到 `/chat`，后端先做意图识别，然后生成一个 plan。  
> 这个 plan 不是写给人看的，而是系统执行路径，比如先查画像、再查活动或统计、最后再生成建议。  
> 执行完以后，我会把 observation、tool trace、memory snapshot 一起返回。  
> 所以这个页面看起来是在展示回答，实际上它展示的是一个可解释 Agent 的内部工作流。  
> 我比较想强调的是，这个项目不只是在“答对问题”，而是在把问题理解、工具调用、证据组织、风险提示和后续训练闭环都打通。

这段话一说，层次会比“这里输入问题，然后出来结果”高很多。

## 你可以重点强调的代码设计点

### 1. 意图分类不是目的，plan 才是关键

在这个项目里，意图分类只是入口。

真正的设计价值是：不同意图会对应不同 plan。

比如：

- 收入解释会查画像 + 统计 + 策略建议
- 活动推荐会查画像 + 活动 + 建议
- 规则答疑会查画像 + 规则库 + 后续动作

你要强调的是：

> 我不是把 query 分个类就结束了，而是把分类结果进一步映射成了不同的执行路径。

### 2. memory 不是装饰，而是影响 plan 和 recommendation

这个项目里 memory 不只是“保存一下历史记录”。

它会真正影响：

- plan 里的 `reason`
- 最终 recommendation 的补充内容
- memory snapshot 的可解释性

你可以说：

> 我希望记忆不是黑盒上下文，而是显式影响系统决策，所以我把它注入到了 planning reason 和 recommendation 生成里。

### 3. answer 不是裸文本，而是 grounded answer

返回结果里不仅有 `answer_summary`，还有：

- `evidence_items`
- `recommendations`
- `risk_notes`
- `tool_trace`

这说明你在做的不是“语言生成”，而是“结构化决策输出”。

### 4. fallback 是预先设计的，不是出错以后补的

当工具出错时，系统会：

- 标记失败 step
- 设置 `fallback_due_to_missing_data`
- 保留失败 evidence
- 给保守建议
- 记录 risk note

这点很值得讲，因为它体现你考虑了生产可用性。

## 评测这块该怎么讲才高级

不要直接说“我还做了个评测脚本”。

建议这样说：

> 我把评测拆成了结果质量和过程质量两部分。结果质量看 intent accuracy，过程质量看 tool coverage、plan validity、evidence coverage 和 fallback rate。因为对 Agent 来说，只看最终回答是不够的，必须看它是不是走了正确路径。

这句话很关键。

然后你可以补一句：

> 当前基线在收入解释、活动推荐、热区建议这几个场景已经能稳定跑通，同时也通过离线评测暴露了规则问答上的分类边界问题。对我来说，这意味着系统具备继续优化的抓手。

这样就不会把自己卡死在 `0.75` 这个数字上。

---

## 训练数据闭环应该怎么讲

你不要说“我导出了 JSONL”。

你应该说：

> 我把训练样本设计成 trace-rich 的格式，不只保留问答对，还保留了 plan、observation、grounded answer 和 failure tags。这样后面无论做 SFT、偏好优化还是 reward 设计，都不是从零开始，而是已经有结构化监督数据了。

这里的关键词要主动说出来：

- trace-rich
- grounded answer
- failure taxonomy
- training flywheel

这几个词会让面试官感觉你理解后训练链路。

## 高频追问，建议怎么答

### 追问 1：为什么这里需要 Agent，而不是纯 RAG？

建议回答：

> 因为这个场景不是单纯查知识。像活动推荐、收入解释、热区建议都需要多源结构化信息组合，还要把工具结果转成行动建议。RAG 更适合知识召回，这里还需要 planning 和 tool orchestration，所以 Agent 更合适。

### 追问 2：为什么要做 memory？

建议回答：

> 因为司机经营问题天然有连续性。上一轮问活动，下一轮问热区，本质上是在同一个经营决策上下文里。如果每轮都完全重置，建议会割裂。这里的 memory 不是无限扩上下文，而是保留少量高价值偏好信息，提升建议连续性。

### 追问 3：你怎么证明这个系统不是“看起来能跑”？

建议回答：

> 我补了离线评测、失败归因和训练样本导出。也就是说，我不仅能展示 happy path，还能显式说明哪里错、为什么错、下一步怎么优化。

### 追问 4：这个系统下一步怎么优化？

建议回答：

> 第一，优化 intent router，把关键词规则升级成更稳的分类器或 prompt-based router；第二，增强 policy QA 的 grounding，把规则问答和活动推荐边界切开；第三，增强前端展示，把 plan、observation、memory 变成结构化面板；第四，把 failure review 进一步接到偏好优化或 reward 设计里。

## 面试时不要这样讲

### 不要只讲“我用了什么技术”

错误讲法：

> 我用了 FastAPI、Pydantic、Typer、pytest。

正确讲法：

> 我用 FastAPI 把在线 demo 服务化，用 Pydantic 约束 Agent 的结构化输入输出，用 Typer 把评测和训练导出做成可复现命令，用 pytest 保证主链路和回退路径可验证。

### 不要只讲“我实现了哪些功能”

功能是最低层。

你要多讲：

- 为什么设计成这样
- 解决了什么问题
- 如何验证它是否工作
- 下一步怎么继续迭代

### 不要把页面当产品 UI 来炫

这个页面不是视觉作品。

它更适合被你定义成“技术 demo 控制台”。

## 最推荐的 3 分钟版本

> 我做这个项目时，先不是直接写 demo，而是先把滴滴相关 JD 做了解析，抽出了它真正看重的能力，比如 Agent 系统设计、后训练、奖励设计、业务指标理解。基于这个能力拆解，我再反推要做什么项目，最后选择了司机经营助手这个场景。  
> 这个场景比较适合讲 Agent，因为司机问题不是纯 FAQ，而是要结合画像、活动、经营统计、规则知识和上下文一起做决策。  
> 所以系统核心链路是 intent router 到 planner，再到 tool execution、memory 和 grounded answer。前端页面只是一个非常轻的入口，但它会把 intent、plan、observation、recommendation 和 memory 都展示出来，正好适合我用来讲 Agent 的内部状态流转。  
> 我觉得这个项目比较有价值的一点是，我没有停留在“功能可演示”，而是继续补了 evaluator、failure review 和 training data export。这样我既能展示现在系统能做什么，也能展示我怎么发现问题、怎么继续优化，甚至怎么把它接到后续的 SFT 或偏好优化实验上。

## 你可以主动承认的优化方向

这部分不要回避，主动讲反而会显得成熟。

### 优化方向 1：提升 intent router

当前规则问答样例存在分类边界问题，说明关键词顺序策略太脆弱。

### 优化方向 2：前端展示从 JSON 控制台升级为结构化面板

现在更适合技术面，不够适合非技术面。

### 优化方向 3：让评测更贴近业务

现在主要是 Agent 过程指标，后面还可以加入司机侧业务收益模拟指标。

### 优化方向 4：把 failure review 真正接到训练环路

现在已经能导出 failure taxonomy，下一步可以把它转成 reward shaping 或偏好数据。

## 如果你只能记住一件事

一定不要把这个项目讲成：

> 我做了一个滴滴司机问答网页。

你要把它讲成：

> 我做了一套从岗位要求理解、到 Agent 系统落地、到评测和训练闭环的垂域项目方法论，并用滴滴司机经营场景把它做成了可运行 demo。

这两句话的含金量完全不一样。

## 可直接照着讲的结尾

> 如果让我总结这个项目，我觉得它最能体现的不是某一个点技术，而是我能把一个岗位要求拆成能力模型，再把能力模型落成一个可运行、可解释、可评测、可继续优化的系统。这也是我希望带给团队的价值，不只是把功能做出来，而是把系统做成一个能持续迭代的工程资产。
